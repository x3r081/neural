Summary

The one-paragraph version

Neural runs OpenAI's gpt-oss-120B, a very large AI model with about 117 billion adjustable settings (called parameters), on one gaming PC with a 12 GiB graphics card and 64 GB of RAM (the computer's main working memory). It runs entirely on this PC and needs no account or subscription. AI models read and write in small pieces called tokens (a token is roughly three quarters of a word). On the latest measurement, both programs were already warm. Neural is ready to answer after a 13,000-token coding prompt in 6.8 seconds, where llama.cpp takes 95.2 seconds. That is about 14 times quicker (13.9×, one run each). When you ask a further question in the same conversation, Neural writes its answer at 24.13 tokens per second against llama.cpp's 15.33, about 57% faster (1.57×). llama.cpp (build b10361) is a widely used open-source program for running AI models locally, and it is the comparison point here. The comparison uses the same PC, the same model file and the same questions, on the same afternoon, with the two programs taking turns.

Why it matters

A very large model, privately, on one PC

The model takes 61 GiB on disk (about 65 GB), roughly the size of a large game install. The graphics card holds 12 GiB, so the model is about five times too big for it (calculated from 61 and 12). Neural writes at 23 to 25 tokens per second on the latest version, several times faster than most people read.

It speaks the OpenAI chat-completions interface (streaming and tool calls), so tools such as Continue in VS Code can connect to it. Not everything the cloud offers is supported (no images, no Responses API, one tool call per response), and Cursor's built-in agent cannot use local models. It is designed to keep everything on the machine; its network traffic has not been audited.

We have not compared running costs against a cloud service, so we make no cost claim here. What the work shows is a capability: a model of this size, at these speeds, on hardware many people already own.

How it works

Send the work to the data, not the data to the work

The model is built from many small specialist networks, called “experts”. Picture a hospital with 36 floors (the model's “layers”) and 128 specialists on each floor. Each token, roughly three quarters of a word, is handled by only 4 per floor. That makes 4,608 specialists in total and 144 used per token, about 3% (a calculation).

The busiest specialists sit in the graphics card's own memory: about 500 of them on the current version, a configuration choice. That is roughly 1 in 10 of the 4,608 (a calculation). The rest stay in the PC's main memory (RAM). The PC's main chip (the processor) uses its eight cores to consult them there, while the card handles its own share at the same time.

The alternative is to copy each missing specialist to the card, about 13 megabytes each time, roughly a large photo. Instead, for each layer, the per-token messages between card and processor are about 23 kilobytes, and the processor does the work where the data sits. A few popular experts are still copied to the card in the background, and long prompts stage experts too. The processor reads RAM at about 36 GB per second on the latest build (Sep 30), against a measured memory ceiling of about 38 to 40 GB per second.

For long inputs, Neural works through the model one floor at a time, so each specialist not on the card is fetched once per floor instead of once per block of the prompt. That cut the 13,000-token prompt from 15.0 to 10.7 seconds. Making the card work on 64 rows of the prompt at a time instead of 16 then took it to 7.7 seconds in like-for-like runs, and 6.8 seconds in the published comparison. Both changes leave the prompt's result identical bit for bit.

Versus llama.cpp

How Neural differs from llama.cpp

llama.cpp is mature and runs on many kinds of computers, which Neural does not (see Limits). For llama.cpp we used the setting tuned for decode speed on this PC (-ncmoe 31, the specialists of 31 of the 36 layers kept in RAM), and it computes them there on the processor. That setting was not tuned for prompt reading. Neural does the same, but it decides for each individual specialist, not for whole layers. It also keeps the ones used most recently on the card, so the choice follows the current conversation.

The gain differs by activity. Prompt reading gains most: llama.cpp with this setting takes 93 to 102 seconds for the same prompt. We did not profile llama.cpp's prompt path; its setting was chosen for answer speed and we did not try a prompt-tuned one, so the prompt ratio is the least conservative of the four. Answers gain less, because both are limited by how fast RAM can be read.

In August our research version lost to llama.cpp, at 13.65 against 13.90 tokens per second. That version copied 1.84 times less data than llama.cpp, but it copied it over the connection between the PC and the graphics card, which is slow. llama.cpp avoided that trip by computing the data where it already sat. The design then changed to a hybrid: for every token, the processor computes the experts held in RAM while the card computes the resident ones. Three research steps took that hybrid from 0.82 times llama.cpp to about 1.5 times on short prompts, and the server versions started from there.

Trust

How we checked it

  • Most speed-ups leave every answer exactly unchanged.
  • A few changes are not bit-identical: the larger expert pool from the rolling K/V cache, the halved admission rate, and the fused core's different summation order. Answers can therefore differ from earlier versions, as this server's answers already can between two runs, because which specialists sit on the card depends on timing.
  • Neural uses OpenAI's published 4-bit (MXFP4) expert weights with the same values (the packed store re-encodes only the scale bytes, losslessly), and nothing is re-quantized or pruned.
  • The fused graphics-card code was tested statistically and stays inside the spread the reference code shows when only its summation order changes (4 sigma, 3 nulls). The later admission changes were not separately quality-tested.
  • Every ratio was measured against llama.cpp on the same day, on the same PC.
  • Where a measurement was not clean, the row says “not measured” instead of showing a number.
  • Failed experiments are kept on record, and reviews corrected our own earlier claims.

Limits

What it does not do

  • It is one PC and one model: Windows, an NVIDIA card with 12 GB or more, and a recent Intel or AMD processor that supports a set of fast maths instructions called AVX-512.
  • It serves one conversation at a time.
  • It can hold 16,384 tokens (roughly 12,000 words, calculated at 0.75 word per token) of conversation at once, and it takes about 2 minutes to start.
  • The expert store (about 55–57 GiB) only just fits in 64 GB next to other programs; the first answer touches some experts for the first time and can also hit disk stalls when free RAM is low (about 55 GiB free is recommended). First-answer speed therefore varies more than follow-ups.
  • The advantage was measured only with the expert store held in RAM. In an earlier research build under RAM pressure, Neural fell to 0.31× llama.cpp (un-replicated). On Sep 5 an earlier build was 2.92× slower than llama.cpp on fresh prompts under background load.
  • Prompt-reading speed on this PC also drifted between days on an unchanged build in September, for reasons not established; the Sep 30 gains are code changes verified against the previous build on the same day.
  • It is a personal server, not a product, and the code is private.

The story

The story in brief

  1. In August the research said no: it reached 0.98 times llama.cpp's speed, and the best it could theoretically reach was 1.17 times (a calculation). The project's own minimum worth building was 1.20 times.
  2. The design changed to a hybrid: for every token, the processor computes the experts held in RAM while the card computes the resident ones.
  3. Over Sep 29 and 30, six passes of measured changes. Each was kept only if it measured faster in like-for-like runs and, where this page says so, gave identical output.
  4. Follow-up answers rose from 1.11× llama.cpp on Sep 23 to 1.57×.
  5. Prompt reading went from 3.1 times llama.cpp on Sep 24 to 13.9 times on Sep 30; the Sep 30 steps are verified code gains.

Next

What would move it further

For prompt reading, the processor side and the graphics-card side now take the same time, about 7.2 seconds for the 13,000-token prompt, so no further change on one side alone helps. For answers, the processor already reads RAM within a few percent of what the memory can physically deliver, and the remaining housekeeping is about 6 thousandths of a second per token; three attempts to hide it gave nothing usable. The software is at its measured balance point. What would move it further is the PC itself: faster memory, or a graphics card with more memory so that more specialists stay on it (each extra percent of specialists on the card is worth about 0.7 thousandths of a second per token, measured). This page makes no purchase recommendation.
